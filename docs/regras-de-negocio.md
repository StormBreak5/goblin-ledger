# Regras de Negócio (Quadro 07)

> Fonte: documento do TC *TCII-N2-IND-Itzac Albertin-Guiliano Rangel Alves* (Google Drive), exportado em 06/10/2026, já com as atualizações pós-implementação. O documento do TC é a fonte da verdade: se houver divergência, atualize este arquivo a partir dele.

| ID | Nome | Descrição e lógica aplicada | RF/RNF associado |
| --- | --- | --- | --- |
| RN01 | Padronização de Moeda Base | O sistema deve somente armazenar valores financeiros em banco de dados na unidade "Cobre" (inteiro absoluto). 1 Ouro = 10000 Cobre; 1 Prata = 100 Cobre. | RNF02 |
| RN02 | Filtro de Liquidez para Modelagem Preditiva | Os algoritmos de Machine Learning só devem processar e gerar projeções preditivas para itens que possuam um volume de negociação superior a 50 unidades nos últimos 7 dias. Itens com baixa liquidez não possuem dados estatísticos suficientes para inferências estocásticas confiáveis, devendo exibir apenas o histórico gráfico (sem a linha de tendência). | RF04 |
| RN03 | Mitigação de Outliers e Market Spoofing | Para evitar que o treinamento do modelo preditivo seja corrompido por manipulações de mercado (jogadores que postam itens a preços absurdamente altos para inflacionar médias), o pipeline de dados (Python) deve descartar registros cujo valor de Buyout seja 300% superior ou 90% inferior à Média Móvel Exponencial (EMA) de 14 dias do referido item. | RF04, RNF01 |
| RN04 | Janela de Retenção e Expiração de Dados | Leilões extraídos da API que não tenham sido atualizados nos últimos 48 horas (tempo máximo de duração de um leilão no jogo) devem ser classificados como "Expirados" ou "Vendidos", encerrando sua influência na cotação em tempo real, mas sendo mantidos no banco de dados sumarizado para compor o histórico de longo prazo. Os leilões classificados como "Expirados" ou "Vendidos" permanecem no detalhamento de leilões por 7 dias; após esse prazo, permanecem somente no histórico consolidado. | RF07 |
| RN05 | Ciclo de Consumo da API (Restrição de Rate Limit) | O sistema não pode realizar requisições à API oficial da Blizzard Entertainment em intervalos menores que 60 minutos para o mesmo endpoint de Auction House, respeitando as políticas de uso da desenvolvedora e garantindo que o IP do servidor não sofra bloqueios temporários. | RF07 |
| RN06 | Cálculo de Valor de Mercado | O "Preço Atual" exibido no dashboard não deve ser o lance mais baixo isolado (Minimum Buyout), que pode ser uma anomalia temporal, mas sim o primeiro quartil (25%) dos preços dos leilões ativos daquele item, garantindo uma representação realista do custo de aquisição para o usuário. O primeiro quartil é ponderado pela quantidade de cada leilão e calculado sobre o preço unitário de compra imediata (Buyout); leilões que possuem somente lance (Bid) não entram no cálculo. | RF03 |
| RN07 | Relevância de Equipamento (iLvl) | O modelo de Machine Learning deve somente processar equipamentos (armaduras/armas) se forem relevantes para o endgame. Equipamentos obsoletos têm a predição bloqueada para economizar processamento. | RF04, RNF04 |
| RN08 | Cota de Alertas por Usuário | O sistema restringe a criação de rastreadores de preços visando performance. | RF05 |
| RN09 | Frescor dos Dados (Cache TTL) | O sistema deve classificar e alertar sobre a latência da informação exibida. Os dados são considerados desatualizados quando a última coleta do mercado do item ocorreu há mais de 24 horas ou quando a última coleta falhou (RN14). | RNF07 |
| RN10 | Limiar de Precisão Preditiva | O sistema deve omitir projeções de ML que não atinjam um padrão mínimo de acurácia matemática. | RF04 |
| RN11 | Validação de Domínio Geográfico | O sistema só aceita o cadastro de contas e a ingestão de dados de mercado das regiões Ocidentais: US e EU. | RF01, RF07, RF11 |
| RN12 | Filtro de Anomalia de Volume | O sistema deve identificar injeções artificiais de itens por bots. É considerado anômalo o volume de um item superior a 10 vezes a mediana dos volumes dos 7 dias anteriores, com piso de 100 unidades e com no mínimo 24 registros anteriores. O registro é marcado como anomalia e mantido no banco de dados. | RF10 |
| RN13 | Snapshot de Estado (Auditoria ML) | O sistema deve consolidar diariamente suas predições contra a realidade para fins de auditoria acadêmica. | RNF04 |
| RN14 | Isolamento de Falhas do Provider | Caso o Provider de um jogo específico apresente falha de comunicação ou retorno de erro 5xx prolongado, o sistema não deve interromper o dashboard principal, devendo exibir uma flag de 'Dados Desatualizados' para o mercado daquele Provider específico. | RNF07, RF07 |
| RN15 | Volume Mínimo para Treinamento Inicial | O modelo preditivo de um item só pode ser processado e ativado (RF12) se a base de dados contiver um período histórico contínuo predeterminado de mínimo 6 meses de registros consolidados para o respectivo ativo. Itens sem histórico mínimo terão a predição bloqueada. O período mínimo corresponde a 180 dias contínuos, e lacunas de até 3 dias sem registros não interrompem a continuidade do período. | RF11, RF12 |
| RN16 | Harmonização de Dados de Terceiros | Dados históricos retroativos obtidos via extração externa (Undermine Exchange, web scraping) devem obrigatoriamente ser convertidos, tipados e higienizados para o exato padrão relacional do SGBD do sistema e da padronização de moeda, garantindo a integridade do dataset antes do treinamento inicial. Cada registro identifica a sua origem e a sua granularidade (diária ou horária). | RF11 |
| RN17 | Marcação Estocástica de Eventos | Datas de grandes atualizações sistêmicas do jogo (patches/expansões) mapeadas no banco histórico devem ser injetadas como variáveis categóricas para o algoritmo. Isso impede que o modelo interprete quedas abruptas de preço causadas por obsolescência de itens como flutuações naturais de mercado. Além de patches e expansões, são registrados como eventos as temporadas, os eventos sazonais e os eventos recorrentes do jogo. | RF11, RF12, RF04 |
| RN18 | Unicidade de Conta por E-mail | Cada endereço de e-mail só pode estar vinculado a uma única conta na plataforma. Por atuar como identificador de acesso do usuário e como destino das notificações de alertas, o e-mail não pode ser alterado após o cadastro. | RF01, RF06 |
| RN19 | Confirmação de Identidade para Operações Sensíveis | Operações que alteram credenciais ou removem dados da conta, como a troca de senha e a exclusão da conta, só podem ser executadas mediante a confirmação da senha atual do usuário, mesmo que ele já esteja autenticado. | RF01, RNF06 |
| RN20 | Exclusão Integral dos Dados do Usuário | Ao excluir a conta, o sistema deve remover de forma definitiva e atômica todos os dados pessoais vinculados ao usuário, sem manter registros residuais, em conformidade com o direito à eliminação dos dados pessoais previsto no art. 18, inciso VI, da Lei Geral de Proteção de Dados (BRASIL, 2018). Caso qualquer etapa da remoção falhe, todas as remoções devem ser desfeitas. | RF01, RF05, RF09 |
| RN21 | Limite de Tentativas de Autenticação | Após cinco tentativas consecutivas de login malsucedidas para um mesmo e-mail, o acesso à conta deve ser bloqueado temporariamente por quinze minutos, mitigando ataques de força bruta. O contador de tentativas é reiniciado após um login bem-sucedido ou ao término do bloqueio. O bloqueio também se aplica a e-mails não cadastrados, para não revelar se o e-mail possui conta. | RF01, RNF06 |
| RN22 | Validade do Link de Recuperação de Senha | O link de redefinição de senha é de uso único e expira em dez minutos após a sua emissão. A emissão de um novo link invalida automaticamente os links anteriores ainda não utilizados. | RF01, RNF06 |
| RN23 | Controle de Ritmo na Extração de Fontes de Terceiros | A extração de dados de fontes de terceiros deve respeitar a cota de requisições definida pela fonte ou, na ausência de cota formal, um intervalo mínimo entre requisições consecutivas, evitando sobrecarregar o serviço de terceiros e o bloqueio do acesso. | RF11 |
